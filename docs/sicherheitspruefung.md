# Sicherheitsprüfung

Stand: 9. November 2026. Geprüft wurde der gesamte Stand des Repositorys: API (`apps/api`),
Web-Oberfläche (`apps/web`), Datenbank (`packages/db`), Container (`infra/docker`,
`docker-compose.yml`), Abhängigkeiten und die Git-Historie. Jeder Punkt nennt den Befund, den
Beleg im Code, was geändert wurde und wie es getestet ist.

## Ergebnis in Kürze

- **Kein kritischer Fund.** Keine Schwachstelle, über die ein Angreifer ohne Konto an Daten käme.
- **Keine geleakten Schlüssel** in der Git-Historie, deshalb muss kein Schlüssel gesperrt werden.
- **Zehn Verbesserungen umgesetzt**, die wichtigsten: Begrenzung der Anmeldeversuche,
  Protokollierung verdächtiger Ereignisse, zwei zusätzliche Security-Header, eine korrigierte
  Proxy-Einstellung im Container und aktualisierte Abhängigkeiten (18 Meldungen auf 3).
- **Drei bewusst getragene Restrisiken**, unten begründet.

## Was der Betreiber selbst tun muss

1. Eigene Werte für `ISMS_JWT_SECRET`, `ISMS_APP_MASTER_KEY` und `ISMS_POSTGRES_PASSWORD` setzen
   (`openssl rand -base64 48`). Die API startet in Produktion nicht mit den veröffentlichten.
2. Hinter TLS `ISMS_COOKIE_SECURE=true` setzen.
3. Steht ein weiterer Reverse Proxy vor nginx, `ISMS_TRUST_PROXY` auf die Zahl der Proxys setzen.
4. `ISMS_REGISTRATION=first` (Standard) oder `closed` lassen, damit niemand Fremdes einen Mandanten anlegt.
5. Abhängigkeiten regelmäßig mit `pnpm audit --prod` prüfen.
